# Two-player browser and native duels

Godot owns rendering and input; `client.js` owns the browser WSS connection and JSON bridge, and `scripts/multiplayer_native_client.gd` implements the same interface with Godot's native WebSocket client. `rules.js` is shared with the dedicated Node server. Build `game-trading-card-server-v4` requires that server, not the previous mesh-v2 signaling service. No client runs authoritative mutation; the host sees only its own hand. Rooms accept exactly two players and start only when both are ready. One opponent is selected automatically.

Keep the curated card rules: 24 Health, 19-card deck (18 starter cards plus one legendary), 8-card hand, 4-unit board, 8 Mana cap, Guard, summoning sickness and increasing fatigue. Turns last 45 seconds. Campaign cooking/rewards/leaderboards are separate. Server-side action IDs, revisions and round IDs prevent duplicate, stale and previous-rematch moves. Never publish an opponent's hand or deck order.

Both players can resume a reserved seat within 90 seconds using tab-scoped credentials. Reload does not destroy server authority. A deliberate leave or expired disconnect forfeits; connection loss pauses the duel during the grace period. Finished duels offer a mutual rematch if both players remain. New players cannot enter a started room. A service restart/expiry ends rooms; no persistence is promised. Invitations carry room credentials in their URL fragment, never endpoint overrides.

The existing same-origin `multiplayer/bootstrap.json` supplies the public endpoint using `signalingUrl`, despite the legacy field name. `config.json` identifies the build and discovery path. Set `signalingUrl` in project `multiplayer/config.json` for Addon Preview and publication; do not rely on inherited Sandbox operator environment variables. Do not put infrastructure settings into player screens. Missing service must show a retry state. Keep `multiplayer/*.js` and `multiplayer/*.json` in exports. Native builds support Host, Join and Reconnect through the same authoritative service.

Native card costs and targeting come from generated `cards.json`. After changing `rules.js`, run `node scripts/generate_multiplayer_cards.mjs` from the project root; the shared rules test checks exact parity. Native metadata is for presentation only; all actions remain server-validated.

When `GAME_MULTIPLAYER_DISCOVERY_URL` is configured, native clients request that operator-owned HTTPS endpoint with the build query parameter and require a matching descriptor with a public WSS endpoint. Discovery failures stay actionable and never fall back to a stale endpoint. Without managed discovery, native clients honor `GAME_MULTIPLAYER_SIGNALING_URL`, then read the preview descriptor from `http://127.0.0.1:3000` (`PORT` or the trusted `previewUrl` config field can select the preview origin). If the preview is offline or returns 404, they can fall back to a project-local bootstrap descriptor or `config.json`'s endpoint. Root-relative `/ws` endpoints resolve against that preview origin. Host and Join retry discovery; an authenticated Reconnect remains pinned to its saved endpoint. Native hosts share a room code accepted by both clients, and native Join also accepts browser invitation links. Closing the native window preserves its seat credentials in the project-scoped user data directory; explicit Leave or Title Screen clears them.

Run `node test/multiplayer_native_test.mjs` from this template to test native clients against an isolated local server. Set `GAME_CARD_SERVER_SOURCE` to the matching service’s `src/server.mjs` with its dependencies installed. It also requires Godot; use `GODOT_BIN` if the executable is not on PATH or installed in `/Applications/Godot.app`.

Maintainer service and deployment instructions: [matching service README](https://github.com/manus-ai/manus-sandbox/blob/476a77047bc977b3e23dfb11b035c6cc715539d4/sandbox/services/game-card-server/README.md). Run its unit/protocol tests and exported-browser acceptance, the shared rules tests in `test/multiplayer_rules.test.mjs`, and the native `test/multiplayer_ui_test.gd`. Browser acceptance covers two seats, private state, readiness, creator/guest reload, results/rematch and leave. Public network acceptance is separate from local tests. Never bake a short-lived Edgegap test URL as permanent hosting. English and Chinese readiness, reconnect and result UI must stay aligned.

Loadouts: choose Balanced/Aggro/Guard, one of five cosmetic heroes, and one legendary in the lobby. Each deck contains 18 starter cards plus exactly one chosen legendary. The server validates `loadout` commands, clears both ready flags on changes, and locks choices after start. Selections persist through reconnect and rematch. All three legendary effects execute on the server.

New Host/Join attempts refresh same-origin discovery. A successfully authenticated seat stores its endpoint in tab-scoped session storage; resume and back/forward-cache restoration return to that endpoint while its room is still alive. Active rooms never migrate when the descriptor changes. Invitations still carry no endpoint override, so rolling deployments need server-side room routing or a drain period before changing discovery.

The service limits new room creation per socket source address to a burst of three, refilling one allowance every 20 seconds. Normal joins and seat resumes do not consume this allowance. Forwarded-IP headers are not trusted: users behind the same reverse proxy can share the allowance, so deployment operators must test proxy behavior before opening the service broadly.
